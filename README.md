# ობიექტების მონიტორინგი — Supabase + GitHub

ქართულენოვანი ფილიალების შემოწმების სისტემა. **HTML/CSS/JavaScript გვერდი GitHub Pages-ზე; ავტორიზაცია და PostgreSQL ბაზა Supabase-ში.** თქვენს კომპიუტერზე მუდმივად გაშვებული Node სერვერი აღარ არის საჭირო.

პროექტი დაკავშირებულია Supabase-ის branch-check პროექტთან. საწყისი სქემა და manage-users ფუნქცია განთავსებულია, მთავარი ადმინისტრატორი გააქტიურებულია. განთავსების ცნობები იხილეთ DEPLOYMENT.md-ში. ქვემოთ მოყვანილია ახალი გარემოს თავიდან გამართვის ინსტრუქცია; უკვე არსებულ ბაზაში საწყისი მიგრაციები ხელახლა არ გაუშვათ. ძველი SQLite ბაზიდან მონაცემები ავტომატურად არ გადადის.

## 1. Supabase პროექტი და ბაზა

შექმენით ახალი Supabase პროექტი. SQL Editor-ში რიგითობით გაუშვით:

1. `supabase/migrations/202610220001_initial.sql`
2. `supabase/migrations/202610220002_user_activation.sql`

ეს ფაილები საწყისი მიგრაციებია და ერთხელ სრულდება. შემდეგ ცვლილებებს დაამატეთ ახალი მიგრაცია. არსებული სხვა აპლიკაციის ბაზაზე ნუ გაუშვებთ.

Authentication-ის პარამეტრებში გამორთეთ **Allow new users to sign up** და anonymous sign-ins. ჩართეთ email/password ავტორიზაცია; პაროლის მინიმუმი დააყენეთ 6 სიმბოლოზე. `supabase/config.toml` ადგილობრივ კონფიგურაციას აღწერს; მისი არსებობა Dashboard-ის პარამეტრებს თავისთავად არ ცვლის.

## 2. პირველი ადმინისტრატორი

Supabase Dashboard → Authentication → Users → Add user/Create user. შექმენით თქვენთვის ანგარიში email-ით **admin@branch-check.invalid** და თქვენი უნიკალური პაროლით (მინიმუმ 6 სიმბოლო), დადასტურებული email-ით. ვებაპში მომხმარებლის სახელი იქნება **admin**. ეს ტექნიკური email-ია; წერილების მისაღებად არ გამოიყენება.

ანგარიშის შექმნის შემდეგ SQL Editor-ში გაუშვით:

```sql
update public.profiles
set name = 'მთავარი ადმინისტრატორი', role = 'admin', active = true
where id = (select id from auth.users where email = 'admin@branch-check.invalid');

select username, name, role, active
from public.profiles where username = 'admin';
```

შედეგი უნდა იყოს ერთი აქტიური admin. სხვა მომხმარებლები დაამატეთ უკვე ვებაპიდან. პაროლები GitHub-ზე, SQL ფაილებში ან ჩატში არ ჩაწეროთ. თუ loginDomain-ს ცვლით, მომხმარებლების ტექნიკური email-ებიც შესაბამის დომენს უნდა იყენებდეს; სამუშაო სისტემაში დომენის შეცვლას ცალკე მიგრაცია სჭირდება.

## 3. მომხმარებლების მართვის Edge Function

Dashboard-იდან შექმენით ფუნქცია სახელით **manage-users** და ჩასვით `supabase/functions/manage-users/index.ts`-ის შინაარსი, ან გამოიყენეთ Supabase CLI:

```text
supabase login
supabase link --project-ref YOUR_PROJECT_REF
supabase functions deploy manage-users --no-verify-jwt
supabase secrets set ALLOWED_ORIGIN=https://YOUR_GITHUB_USERNAME.github.io
supabase secrets set LOGIN_DOMAIN=branch-check.invalid
```

`--no-verify-jwt` თიშავს მხოლოდ gateway-ის ძველ JWT შემოწმებას. ფუნქცია თავად ამოწმებს Bearer ტოკენს `auth.getUser(token)`-ით და მოქმედი ადმინისტრატორის როლს. ავტორიზაციის კოდი არ წაშალოთ. Dashboard-ით განთავსებისას ანალოგიურად გამორთეთ ფუნქციის legacy JWT verification და Secrets-ში შეიტანეთ ზემოთ მითითებული ორი პარამეტრი.

`ALLOWED_ORIGIN` არის მხოლოდ სქემა+დომენი, რეპოზიტორიის გზისა და ბოლო `/`-ის გარეშე. მაგალითად, გვერდისთვის `https://ana.github.io/branch-check/` მიუთითეთ `https://ana.github.io`. საკუთარ დომენზე გადასვლისას ეს პარამეტრიც განაახლეთ. ლოკალური სრული შემოწმებისთვის დროებით გამოიყენეთ `http://localhost:3000` და ბოლოს აღადგინეთ რეალური დომენი.

ფუნქცია Supabase-ის სერვერულ გარემოში იყენებს `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`-ს. Hosted Supabase ამ ჩაშენებულ ცვლადებს უზრუნველყოფს. **service_role / sb_secret არასდროს გადაიტანოთ ბრაუზერის ფაილში ან GitHub-ზე.** მხოლოდ საჯარო გასაღებით ბრაუზერიდან სხვა მომხმარებლის შექმნა ან პაროლის შეცვლა დაუშვებელია; ამიტომ საჭიროა Edge Function.

ანგარიშის შექმნა Auth-სა და პროფილში ორ ეტაპად ხდება. გაუმართაობისას ანგარიში რჩება გამორთული; ადმინისტრატორმა მომხმარებლების გვერდიდან უნდა შეამოწმოს როლი და აღადგინოს. წარუმატებელი შექმნის შემდეგ იმავე სახელით ბრმად ნუ გაიმეორებთ დამატებას.

## 4. საჯარო კონფიგურაცია

Supabase Project Settings/API Keys-იდან აიღეთ Project URL და **publishable key** (ან legacy anon key). შეცვალეთ `web/config.js`:

```javascript
window.APP_CONFIG = {
  supabaseUrl: 'https://YOUR_PROJECT.supabase.co',
  supabasePublishableKey: 'sb_publishable_YOUR_PUBLIC_KEY',
  loginDomain: 'branch-check.invalid'
};
```

ეს ორი მნიშვნელობა საჯაროა; მონაცემებს იცავს RLS და სერვერული ფუნქციები. ბრაუზერის კონფიგურაციაში service_role გასაღების ჩაწერა აკრძალულია.

## 5. ატვირთვა GitHub-ზე

შექმენით GitHub რეპოზიტორია, მაგალითად `branch-check`. **ამ საქაღალდის შიგთავსი** ატვირთეთ რეპოზიტორიის მთავარ დონეზე: იქვე უნდა ჩანდეს `web`, `supabase`, `scripts`, `.github` და `package.json`. არ ატვირთოთ ZIP ფაილი როგორც აპლიკაცია — ჯერ ამოარქივეთ.

მთელი საქაღალდის გადატანა ყველაზე საიმედოა GitHub Desktop-ით ან Git-ით. ვებინტერფეისით ატვირთვისას განსაკუთრებით შეამოწმეთ, რომ `.github/workflows`-იც აიტვირთა. პაროლები და სერვერული გასაღებები არ დაამატოთ.

რეპოზიტორიაში გახსენით **Settings → Pages → Source: GitHub Actions**. გამოიყენეთ `main` ბრენჩი. Push-ის შემდეგ `Publish GitHub Pages` გამოაქვეყნებს მხოლოდ `web/` საქაღალდეს. მიგრაციები და Edge Function არ ხდება გვერდის ნაწილი. `config.js`-ის შეუვსებლობისას გამოქვეყნება განზრახ შეჩერდება.

საიტის მისამართი იქნება `https://YOUR_GITHUB_USERNAME.github.io/branch-check/`. Supabase Auth-ის URL Configuration-ში Site URL-ად ჩაწერეთ ეს სრული URL. საჭიროების შემთხვევაში მიუთითეთ შესაბამისი redirect URL-იც; მიმდინარე პაროლით შესვლა redirect-ს არ იყენებს.

GitHub Actions-ის `Project checks` ამოწმებს ექსპორტს/ფაილებს და იზოლირებულ Supabase გარემოში — მონაცემთა ბაზის უფლებებს. პირველი მიგრაციები გამოიყენება ადგილობრივ სატესტო გარემოში, თქვენს hosted ბაზაში ავტომატურად არ სრულდება. Supabase CLI ვერსია CI-ში `latest`-ია; პროექტის შემდგომი სტაბილიზაციისას დაფიქსირეთ წარმატებით გამოცდილი ვერსია.

GitHub Pages-ის გვერდი და ბრაუზერის კოდი შეიძლება საჯაროდ იყოს ხელმისაწვდომი; შემოწმებების მონაცემები ავტორიზაციისა და როლების გარეშე არ იკითხება. რეპოზიტორიის private/public არჩევა გააკეთეთ თქვენი GitHub გეგმისა და Pages-ის ხელმისაწვდომობის მიხედვით.

## 6. Codex-ში გაგრძელება

რეპოზიტორია გახსენით Codex-ში პროექტად. შემდეგ ცვლილებები, ტესტები და Git-ის ისტორია იმავე პროექტში გაგრძელდება. ეს ZIP არ შეიცავს თქვენს GitHub ანგარიშთან მიბმულ რეპოზიტორიას ან სხვა ჩატის იდენტობას.

## შესაძლებლობები

- ადმინისტრატორი: ფილიალების/კითხვების დამატება, ტექსტის შეცვლა, არქივში გადატანა და აღდგენა; მომხმარებლების შექმნა, სახელის/როლის ცვლილება, გათიშვა/აღდგენა და პაროლის შეცვლა.
- ინსპექტორი: აქტიური ფილიალის არჩევა, ყველა შესაბამის კითხვაზე 1–5 შეფასება, კომენტარი და შენახვა.
- საერთო კითხვა ყველა ფილიალზე მოქმედებს; კონკრეტულ ფილიალზე მიბმული — მხოლოდ მასზე.
- შემოწმება და პასუხები ერთ ტრანზაქციაში ინახება; ბაზა ამოწმებს პასუხების სისრულეს, მიმდინარე კითხვებს, შეფასებებსა და დუბლირებას. ორმაგი დაჭერა მეორე ჩანაწერს არ ქმნის.
- ისტორიული ფილიალის, ავტორისა და კითხვების სახელები ასლებად ინახება. არქივი, როლის ცვლილება და ტექსტის რედაქტირება ისტორიას არ ცვლის.
- ანგარიშები, თარიღისა და ფილიალის ფილტრები, საშუალო შეფასება და დაბალი ქულების რაოდენობა; თარიღის საზღვრები თბილისის დროით.
- ეკრანზე ბოლო 200 გაფილტრული შემოწმება, სტატისტიკა მთელ ნაკრებზე. უფრო ძველი ჩანაწერებისთვის შეამცირეთ პერიოდი.
- ნამდვილი `.xlsx` ექსპორტი, თითო პასუხი ცალკე სტრიქონად, მაქსიმუმ 50 000 პასუხი. ტექსტი ფორმულად არ სრულდება.

## უსაფრთხოება და შეზღუდვები

ყველა მონაცემთა ცხრილზე RLS ჩართულია. ინსპექტორი ვერ კითხულობს ანგარიშებსა და სხვის პროფილებს და ვერ წერს პირდაპირ ცხრილებში. RPC ავტორიზაციას ყოველი მოთხოვნისას პროფილის აქტიურობითა და როლით ამოწმებს; მომხმარებელს თავისი metadata-დან admin როლის მინიჭება არ შეუძლია. ახალი Auth ანგარიში ყოველთვის გამორთული ინსპექტორია, სანამ ადმინისტრატორი არ გაააქტიურებს. საკუთარი admin-ის გათიშვა/დაქვეითება დაბლოკილია.

პროფილის როლის ან active სტატუსის შეცვლა ბაზაზე შემდეგივე მოთხოვნაზე მოქმედებს, უკვე გაცემული JWT-ითაც. Auth პაროლის შეცვლა უკვე გაცემულ ყველა access token-ს თავისთავად მყისიერად არ აუქმებს; ტოკენების ვადასა და სესიების პოლიტიკას Supabase-ში მართავთ. გადაუდებელი წვდომის შესაწყვეტად გათიშეთ პროფილი. აპიდან გასვლა ასრულებს მიმდინარე ბრაუზერის სესიას. სესია ინახება sessionStorage-ში, მხოლოდ ამ ჩანართისთვის. გარე Supabase SDK იტვირთება esm.sh-დან ფიქსირებული ვერსიით.

ეს ვერსია იყენებს ტექნიკურ email-ებს მომხმარებლის სახელით შესანარჩუნებლად; ელფოსტით პაროლის აღდგენა არ მუშაობს — პაროლს ადმინისტრატორი ცვლის. MFA, ფოტოები და ოფლაინ რეჟიმი ჯერ არ შედის. სარეზერვო ასლები და მათი აღდგენის გამოცდა მოაწყვეთ Supabase-ში თქვენი გეგმის მიხედვით. არც სერვერული საიდუმლო გასაღები და არც მომხმარებელთა მონაცემები კოდის რეპოზიტორიაში არ შეინახოთ.

## ლოკალური ნახვა და ტესტები

საჭიროა Node.js 22.13+ (რეკომენდებულია 24). დამატებითი პაკეტები არ სჭირდება:

```text
node scripts/preview.mjs
node --test scripts/check.test.mjs
```

გახსენით `http://localhost:3000`. კონფიგურაციის გარეშე გამოჩნდება დაყენების გვერდი. HTML-ს პირდაპირ `file://` რეჟიმში გახსნა JS მოდულებისა და ავტორიზაციის გამო არ გამოიყენოთ.

ბაზის ინტეგრაციული შემოწმება საჭიროებს Supabase CLI-სა და Docker-ს:

```text
supabase start
supabase test db
supabase stop
```

`supabase/tests/permissions.sql` გამოიყენეთ მხოლოდ იზოლირებულ სატესტო ბაზაში. მონაცემები rollback-დება, მაგრამ identity sequence შეიძლება წინ წავიდეს. თქვენს ანგარიშში რეალური შესვლის, ფუნქციის განთავსებისა და Pages-ზე სრული სცენარის შემოწმება ცალკე ნაბიჯია; მხოლოდ ფაილების ტესტების გავლა ამას არ ადასტურებს.

ოფიციალური წყაროები: [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [Database functions](https://supabase.com/docs/guides/database/functions), [Auth Admin createUser](https://supabase.com/docs/reference/javascript/auth-admin-createuser), [GitHub Pages publishing](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site).
